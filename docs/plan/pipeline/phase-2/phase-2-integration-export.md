## Description

Wire the research brief into the export pipeline so that generated research can be included in Word/PDF exports alongside the timeline. Also link timeline events to relevant legal precedents from the research brief. End-to-end test covering the full Phase 1 + Phase 2 flow.

## Goals

- Add optional research brief section to Word (.docx) and PDF exports.
- Accept `include_research` query parameter in export API endpoint.
- Link timeline events to their relevant legal precedents (via citations from research).
- Display precedent links in the timeline view (optional — stretch).
- End-to-end test: matter upload → document processing → timeline generation → research brief → export with brief.
- Ensure all existing tests still pass.

## Workflow

```
Existing export flow (timeline only)
  → Add `include_research` option
  → Fetch research brief from BriefGenerator cache (Group B)
  → Append "Research Brief" section to docx/pdf
  → Return combined export
```

```
Timeline event → research citation linking
  → After brief generation, map event dates/parties to cited cases
  → Store links (event_id ↔ corpus_document_id) in a new junction table or metadata
  → Display precedent badge on timeline events
```

## Considerations

- **Backward compatibility**: The default `include_research=false` ensures existing export behavior is unchanged. All existing tests must pass without modification.
- **Brief not available**: If the research brief hasn't been generated yet and `include_research=true`, export proceeds without the research section (no error). The UI should guide the user to generate a brief first.
- **Large briefs**: A research brief with many sections and citations could make the export file large. For docx, this is fine; for PDF, ensure page breaks work correctly.
- **Related citations on timeline view**: This is a "nice to have" stretch goal. If time is constrained, skip Step 4 (precedent badges) and focus on the export integration.
- **Migration strategy**: The `related_citations` column addition should be safe for SQLite (just add the column — SQLite ignores if column exists with a warning). Consider adding a migration script if using PostgreSQL in production.
- **Timing**: Group D must be implemented after Groups A, B, C are merged because it imports concrete service classes from all three groups. The E2E test especially depends on all components being present.
- **E2E test hermeticity**: Use `QdrantClient(memory=True)` for the vector store, SQLite in-memory for the database, and mock all LLM calls. The test should run without any external services or API keys.
